# 투표지(ballots) 테이블을 추가하고, 예정·진행 중·마감됨 상태는 DB 시각으로 계산한다

실명 투표(누가 무엇을 골랐는지)와 복수 선택(한 번에 여러 선택지)을 지원하려면 선택지별 득표 카운터(`options.vote_count`)만으로는 부족하다. 그래서 투표 행위 한 번을 `ballots`(투표자 이름 nullable)와 `ballot_choices`(고른 선택지들)로 기록하기로 했다. 다만 이미 쌓인 득표는 투표지 기록 없이 카운터에만 있으므로 카운터는 없애지 않는다. 투표 행위 시 투표지 기록, 선택지 카운터, 투표자 수(`polls.ballot_count`)를 한 SQL 문장에서 함께 늘려 값이 어긋나지 않게 한다. 득표율의 분모는 투표자 수다(복수 선택이면 합이 100%를 넘는다).

실명 투표의 1인 1표는 쿠키에 더해 `(poll_id, lower(voter_name))` 부분 유니크 인덱스로 DB가 보장한다. 이름은 본인 확인이 아니라 자기 신고이므로 다른 사람 이름으로 투표하는 것은 막지 못한다(ADR-0001의 신뢰 수준 유지).

예약된 시작·종료는 스케줄러(cron) 없이 처리한다. 상태(예정/진행 중/마감됨)는 조회할 때마다 `opens_at`, `closes_at`과 DB의 `now()`를 비교해 계산하고, 투표 행위 SQL도 같은 조건으로 거부한다(ADR-0002 확장). 그래서 "자동 시작·종료"와 "마감 후 자동 결과 공개"에 백그라운드 작업이 필요 없다.

투표가 하나라도 들어온 뒤에는 선택 방식과 공개 방식을 바꿀 수 없다. 이미 기록된 투표지의 의미가 바뀌기 때문이다.

## Consequences

- 설정 잠금(선택 방식·공개 방식, 시작 시각을 미래로 옮기기)은 UPDATE의 WHERE 조건에 두고, 투표 행위는 투표 행을 `for update`로 잠근다. 동시에 들어온 수정과 투표 행위가 서로의 판정을 건너뛰지 못한다.
- 실명 투표에서도 브라우저 쿠키 검사가 먼저 적용된다. 한 기기를 여러 사람이 함께 쓰면 두 번째 사람은 그 기기로 투표할 수 없다(동아리 방 공용 PC라면 시크릿 창을 쓴다).
- 마감 후 공개 + 실명 투표에서 "이 이름으로 이미 투표했습니다" 응답으로 특정 이름의 참여 여부는 알 수 있다. 무엇을 골랐는지는 드러나지 않으며, ADR-0001의 신뢰 수준에서 받아들인다.
- 배포 순서: DB 마이그레이션(추가만 함) → 새 코드 배포. 옛 코드가 마이그레이션 뒤 잠깐 돌면 그 사이 투표자 수(ballot_count)가 늘지 않을 수 있다.
